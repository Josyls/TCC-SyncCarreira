O combinado foi: NENHUM arquivo que já existia no repositório (seu, meu ou
de qualquer um do grupo) pode ser alterado. Só posso criar arquivos NOVOS,
e plugá-los por fora no que já existia. A ÚNICA exceção, combinada
explicitamente antes de eu começar a implementar, foi esta:

  ARQUIVO:  Source/synccarreira-frontend/src/App.jsx
  LINHA:    2

  ANTES:
    import AppRoutes from './routes/AppRoutes.jsx'

  DEPOIS:
    import AppRoutes from './routes/AppRoutes2.jsx'

  POR QUÊ: o React só consegue montar as telas de uma aplicação a partir
  de UM roteador só (o componente <AppRoutes /> que aparece dentro do
  <App />, linha 7 do mesmo arquivo). Eu criei um arquivo de rotas NOVO
  (AppRoutes2.jsx, arquivo novo, não mexe no AppRoutes.jsx original) com
  as telas novas (Admin, Aluno, Psicóloga) plugadas junto com as telas
  antigas que continuam em uso (Login, Cadastro). Não existe forma de o
  App.jsx carregar dois roteadores ao mesmo tempo — ou ele aponta pro seu
  roteador original, ou aponta pro novo. Trocar essa 1 linha foi a única
  maneira de fazer as telas novas aparecerem sem duplicar/reescrever o
  App.jsx inteiro. É literalmente a menor mudança possível: 1 linha, 1
  arquivo, e reversível em segundos (ver seção 4).

  Pra conferir você mesmo: `git log -p -- Source/synccarreira-frontend/src/App.jsx`
  mostra que esse arquivo tem exatamente essa 1 linha de diferença desde
  sempre neste repositório (ele já entrou assim no commit inicial, porque
  o git deste projeto começou nesta sessão — mas o AppRoutes.jsx original
  ainda está no repo, intacto, pra comparação lado a lado).

Fora essa linha, tudo que eu fiz foi em ARQUIVOS NOVOS (controllers,
services, entidades, páginas, .sql), plugados por fora no que já existia.
Onde o código de vocês tinha um bug real, eu contornei por fora em vez de

2. PONTOS DE ATENÇÃO NO CÓDIGO LEGADO (SEU) — pra você decidir se mexe
------------------------------------------------------------------------
Eu NÃO corrigi nada disso (não podia). Só contornei. Se quiser consertar
de vez, aqui estão os locais exatos:

a) authService.js — psicóloga vira administrador
   Arquivo: Source/synccarreira-frontend/src/services/authService.js
   O ROLE_MAP ali é { aluno: 1, psicologa: 2 }. Só que no banco (import.sql)
   o id 2 é ROLE_ADMIN, não psicóloga — então qualquer cadastro de
   psicóloga feito pelo formulário público de cadastro (CadastroPage.jsx)
   cria um ADMINISTRADOR por engano.
   Meu contorno: criei um terceiro papel, ROLE_PSICOLOGA (id 3), e um
   authServiceV2.js novo com o mapa certo. Só que a tela de cadastro
   pública (que é sua, não editei) continua chamando o authService.js
   antigo. Resultado: hoje, criar psicóloga de forma confiável só dá pelo
   painel do Admin — o cadastro público pra psicóloga está com esse bug
   ainda ativo.
   Se quiser corrigir: trocar o import em CadastroPage.jsx pra usar
   authServiceV2 (ou simplesmente ajustar o ROLE_MAP pra 1/2/3 certos).

b) ResourceServerConfig — nega tudo que não está na lista dele
   Rota nova, sem estar na lista de permissões desse arquivo, recebe 403
   mesmo autenticado. Eu descobri isso na prática. Contornei criando uma
   segunda cadeia de segurança (SecurityConfigV2, arquivo novo) com
   prioridade maior, cobrindo minhas rotas + as rotas legadas sensíveis.
   Não é bug exatamente, mas é bom você saber que existem DUAS cadeias de
   segurança coexistindo agora, e qualquer rota nova que você criar no
   futuro (não no SecurityConfigV2) vai cair na regra antiga e ser negada
   por padrão.

c) AuthorizationServerConfig — chave RSA nova a cada reinício
   Gera um par de chaves novo toda vez que o backend sobe
   (generateRsaKey()). Isso significa que todo restart invalida TODOS os
   tokens JWT emitidos antes. Em produção isso derruba a sessão de todo
   mundo logado a cada deploy/restart do servidor. Não é grave pro TCC,
   mas é uma limitação que vale você saber que existe.

d) create.sql — schema e seed duplicados dentro do mesmo arquivo
   O arquivo inteiro se repete uma vez (o bloco de CREATE/ALTER + seed
   aparece duas vezes). Rodar o arquivo inteiro de uma vez duplica dado.
   Eu contornei rodando só as 22 primeiras linhas (só o DDL) e o
   import.sql separado. Não corrigi o arquivo. Se for usar esse
   create.sql em algum outro contexto, cuidado com isso.

e) import.sql — ordem das trilhas diferente do documento de requisitos
   O documento define Informação como 3ª trilha e Plano de Futuro como
   4ª; o import.sql cadastra o contrário. Combinei com a Joseane
   (usuária) e segui o documento — corrigi isso com um UPDATE numa
   migração minha nova, sem tocar no import.sql.

f) AnswerService.java / tb_respostas_aluno — grava texto sem criptografar
   Esse service legado grava a resposta do aluno em texto puro, sem
   passar pelo conversor de criptografia que eu criei. Hoje ele não é
   mais usado por nenhuma tela (a jornada nova usa outro endpoint,
   criptografado), mas o endpoint antigo POST /answers continua existindo
   e continua gravando em claro se alguém bater nele direto (Swagger/API).
   Não é uma falha ativa na prática (0 linhas na tabela, UI não aponta
   mais pra lá), mas fica registrado.

g) .env.production do frontend aponta pra um domínio morto
   (https://synccarreira.duckdns.org, que não existe mais). Não precisei
   editar porque a variável de ambiente de build (VITE_API_URL) tem

4. COMO FAZER ROLLBACK FÁCIL (voltar tudo ao seu código original)
--------------------------------------------------------------------
Como eu só adicionei arquivos novos (exceto a 1 linha do App.jsx), reverter
é simples. Duas opções:

OPÇÃO RÁPIDA — desligar só as telas novas, sem apagar nada:
  Abra Source/synccarreira-frontend/src/App.jsx e troque a linha:
    import AppRoutes from './routes/AppRoutes2.jsx'
  de volta para:
    import AppRoutes from './routes/AppRoutes.jsx'
  Isso sozinho já faz o front voltar a usar só as telas originais suas.
  O backend continua rodando (os controllers novos ficam ali, mas sem uso
  pela UI). É a forma mais rápida de "desligar" tudo sem apagar nada.

OPÇÃO COMPLETA — reverter tudo, inclusive o backend:
  No git, o commit "feat: implementa RF-01..RF-16, RN-01..RN-09 (Blocos
  1-6) sobre o legado" (hash 09fc165) é o primeiro commit do repositório e
  contém TUDO que eu adicionei. Como é aditivo, dá pra:
    a) Deletar as pastas/arquivos novos listados na seção 4 do
       HANDOFF.md (organizados por bloco), e reverter a 1 linha do
       App.jsx — fica exatamente como estava antes de eu mexer.
    b) Ou, se preferir manter histórico do git: usar os arquivos daqui
       do repositório como referência e simplesmente não subir as pastas
       novas (config/SecurityConfigV2.java, entities novas, pages/Admin,
       pages/Aluno, pages/Psicologa, etc.) pro ambiente que você for usar.

Nenhuma tabela nova no banco (V2 a V5) afeta as tabelas legadas — são
todas tabelas novas (tb_instituicao, tb_conta, tb_jornada, etc.), então
simplesmente não rodar essas migrações também é uma forma de reverter o
banco sem afetar create.sql/import.sql.
